# Demo walkthrough

A scripted, end-to-end demonstration of the AI Hotel Intelligence Platform. It takes a reviewer
from a fresh clone to a running stack with seeded demo data, through every screen in a sensible
order, and then into the code, the tests and the evaluation records behind those screens.

It is written for three readers: a university examiner, a software-engineering interviewer, and
a developer cloning the repository for the first time. Each step says where to go, what to do,
what you should see, and what the step demonstrates.

> **Scope.** This is an academic and professional portfolio project (roadmap decision R5,
> [roadmap-v2.0-execution.md §3.13](roadmap-v2.0-execution.md#313-product-reach-r5)). It is
> **demo ready and not production ready**: see [Limitations to state during the demo](#limitations-to-state-during-the-demo)
> and the [closure audit](project-closure-audit.md).

> **The data is synthetic.** Every hotel, guest, booking, payment, review and ledger line in this
> walkthrough is generated by `scripts/seed_demo.py`. Every name and address is invented, and every
> email address is under `example.com`. It is **not** real hotel data, and it is **not** the data
> any model was trained or evaluated on. That is a separate, published dataset; see
> [Two datasets, never mixed](#two-datasets-never-mixed).

## How this walkthrough was verified

- **Route A, the local stack, was run end to end on 2026-11-27** against a new, empty database,
  with the commands below:
  - creating, migrating and seeding the database;
  - starting the API and the frontend dev server;
  - the readiness checks;
  - signing in as the seeded owner through the API;
  - every endpoint each screen in part C reads.

  The screens themselves are described from their source, and the Vitest suite and CI's
  responsive audit render them.
- **Route B, Docker Compose, was not run for this document.** Its commands are the ones CI's
  `Responsive audit` job runs on every push (`.github/workflows/ci.yml`): build and start the
  stack, seed it with `scripts/seed_demo.py` through the `migrate` image, grant the demo owner
  platform administration, then sign in and render 17 routes in Chromium.
- **Figures quoted below are examples from that run**, with the default seed `7151` and reference
  date 2026-11-27. They depend on the reference date. Everything else, such as headings, labels,
  states and refusals, does not.

## Two datasets, never mixed

| | Synthetic demo data | Published evaluation dataset |
|---|---|---|
| What | Two fictional hotels, *Demo Harbour Hotel* and *Demo Hillside Inn* | *Hotel booking demand datasets* (Antonio, de Almeida & Nunes, 2019), CC BY 4.0, [10.1016/j.dib.2018.11.126](https://doi.org/10.1016/j.dib.2018.11.126) |
| Source | Generated by `scripts/seed_demo.py`, deterministic for a seed and reference date | Bookings at two real Portuguese hotels (2015–2017), with identifying fields removed by its authors |
| Where it lives | In the demo database you create below | `ml/data/`, recorded in [ml-training-data.md](ml-training-data.md) |
| Used for | Looking at the screens | Training `demand_baseline_v1`, its backtest, and the frozen hold-out evaluation ([ml-frozen-holdout-evaluation.md](ml-frozen-holdout-evaluation.md)) |
| Evidence of | Nothing. It is never used to train, evaluate or measure anything | What those records say, for those two hotels, and nothing beyond them |

The demand estimate on the Analytics screen comes from the model trained on the published
dataset, applied to the synthetic hotels. That mismatch is visible on screen (step C10), and it
is a limitation, not a result.

## A. Preparation

Two routes. Route A is quicker to inspect: the API's interactive documentation is reachable, and
the optional local copilot can work. Route B is the deployed topology: TLS through nginx, with the
model packaged in the image. Pick one; both end at the same sign-in screen.

Commands are written for a Bash shell from the repository root, as in the root README. On
Windows, use Git Bash and `.venv/Scripts/python.exe`; on macOS or Linux, use `.venv/bin/python`.

### A.1 Prerequisites

| Needed for | What | Version used here |
|---|---|---|
| Both routes | Git | any |
| Route A | Python | 3.14.7 (the floor is 3.12) |
| Route A | Node.js and npm | Node 24.21.0, npm 11 |
| Route A | A PostgreSQL server you control | 18.6. The schema needs a real PostgreSQL: there is no SQLite fallback |
| Route B | Docker with Compose, and OpenSSL for a local certificate | Compose v2 |
| Optional, Route A only | [Ollama](https://ollama.com/) running on the same machine, with a model pulled | `qwen3.5:4b` is the default model name |

Nothing in this walkthrough needs a paid service, an API key or network access beyond installing
packages and Docker images.

### Route A: the local stack (verified 2026-11-27)

**A.2 Install.**

```bash
python -m venv .venv
```

```bash
.venv/Scripts/python.exe -m pip install --require-hashes -r backend/requirements-dev-lock.txt
```

```bash
cd frontend && npm ci && cd ..
```

**A.3 Create a new, empty demo database.** Use a name **without** the `_test` suffix, so the
integration suite can never reach it, and one that does not exist yet:

```bash
psql -U postgres -c "CREATE DATABASE hotel_intelligence_demo"
```

Any other client works, for example `createdb -U postgres hotel_intelligence_demo`. Below,
`<password>` is your PostgreSQL user's password. Nothing in the repository holds it.

**A.4 Migrate it.**

```bash
.venv/Scripts/python.exe -m alembic -x url=postgresql+psycopg://postgres:<password>@localhost:5432/hotel_intelligence_demo upgrade head
```

Expected: the last line is `Running upgrade 0022_catalogue_versions -> 0023_auth_sessions`.
Check it with `current` in place of `upgrade head`, which prints `0023_auth_sessions (head)`.

**A.5 Seed the synthetic demo data.** Choose the demo owner's password, 12 to 256 characters.
It is read from the environment, never printed, and never written to the repository:

```bash
export DEMO_OWNER_PASSWORD='<choose one>'
```

```bash
.venv/Scripts/python.exe scripts/seed_demo.py --database-url postgresql+psycopg://postgres:<password>@localhost:5432/hotel_intelligence_demo --reference-date today
```

Expected:
- the output ends with a `plan fingerprint` and a `database fingerprint`, and the two are equal;
- it lists row counts per table. On 2026-11-27 these were 2 hotels, 25 rooms, 2181 guests, 2483
  bookings, 669 reviews, 3917 revenue and 314 expense lines, 1 user and 2 declared observation
  periods.

The script refuses a database that already holds any row, and it never deletes or migrates
anything. Options (`--seed`, `--history-days`, `--future-days`, `--owner-email`, `--dry-run`) are
in the [database README](../database/README.md#demo-data).

**A.6 Start the API.** Two variables are needed: the database, and a signing secret for the
session tokens. The API runs without `SECRET_KEY` in development, but the first sign-in fails:
there is deliberately no built-in default.

```bash
export DATABASE_URL=postgresql+psycopg://postgres:<password>@localhost:5432/hotel_intelligence_demo
```

```bash
export SECRET_KEY="$(.venv/Scripts/python.exe -c 'import secrets; print(secrets.token_urlsafe(48))')"
```

```bash
.venv/Scripts/python.exe -m uvicorn app.main:app --app-dir backend --reload
```

Instead of exporting them, you can put the same variables in a `.env` file copied from
`.env.example`, which is git-ignored. Never commit a value.

**A.7 Start the frontend** in a second shell:

```bash
cd frontend && npm run dev
```

The dev server is `http://localhost:5173`. It proxies `/api` to `http://localhost:8000`, so the
browser stays on one origin.

**A.8 Check that it is ready.**

| Open | Expected |
|---|---|
| http://localhost:8000/health | `{"status":"ok", …, "environment":"development"}` |
| http://localhost:8000/health/db | `{"status":"ok","application":"running","database":"reachable", …}` |
| http://localhost:8000/api/v1/ | `{"name":"AI Hotel Intelligence Platform", …, "copilot_enabled":false}` |
| http://localhost:5173 | the **Sign in** screen |

**A.9 Optional: platform administration**, needed only for the Platform screen (step C14). It is
an audited operator command, and there is deliberately no API for it. Run it with the same
`DATABASE_URL`:

```bash
PYTHONPATH=backend .venv/Scripts/python.exe -m app.jobs.platform_admin grant demo.owner@example.com
```

Expected: `platform administration granted; 1 administrator(s)`.

**A.10 Optional: the demand model's payload.** The Analytics screen's demand estimate needs the
fitted payload `ml/models/demand_baseline_v1/model.pkl`. It is generated, never committed, and a
fresh clone does not have it. Without it the panel says **No estimate for tomorrow**, which is the
designed refusal rather than a fault. Generating it is offline ML work, described in
[ml/README.md](../ml/README.md) and [ml-production-runtime.md](ml-production-runtime.md). Route B
builds and verifies it inside the image, so there the panel works with no extra step.

### Route B: Docker Compose (the commands CI runs)

**A.11 Configure.** Copy the template, then set two values in `.env`: `POSTGRES_PASSWORD`, without
which Compose refuses to start, and `SECRET_KEY`, without which sign-in fails. Generate each with
`openssl rand -hex 24` or similar.

```bash
cp .env.example .env
```

**A.12 Create a local certificate.** The stack terminates TLS and will not start without one:

```bash
mkdir -p certs && chmod 700 certs && openssl req -x509 -newkey rsa:2048 -nodes -keyout certs/privkey.pem -out certs/fullchain.pem -days 365 -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1" && chmod 600 certs/privkey.pem
```

**A.13 Build and start the stack.**

```bash
docker compose up -d --build
```

Startup is gated: `db healthy → migrate exits 0 → api healthy → frontend starts`. The `migrate`
service runs `alembic upgrade head` into the new volume. Wait until `docker compose ps` shows the
frontend as healthy.

**A.14 Seed the synthetic demo data**, through the image the stack runs, into the empty migrated
database. This is the command CI's `Responsive audit` job uses. `hotel` and
`hotel_intelligence` are the Compose defaults for `POSTGRES_USER` and `POSTGRES_DB`:

```bash
export DEMO_OWNER_PASSWORD='<choose one>'
```

```bash
docker compose run --rm --no-deps -T -e DEMO_OWNER_PASSWORD -v "$PWD/scripts:/app/scripts:ro" migrate python scripts/seed_demo.py --database-url "postgresql+psycopg://hotel:<POSTGRES_PASSWORD>@db:5432/hotel_intelligence" --reference-date today
```

The expected output is as in A.5. For the optional platform grant (A.9), the Compose form is:

```bash
docker compose run --rm api python -m app.jobs.platform_admin grant demo.owner@example.com
```

**A.15 Check that it is ready.** Open **https://localhost:8443**. The browser warns once about the
self-signed certificate, and then shows the **Sign in** screen. http://localhost:8080 only
redirects there. nginx is the only published service: the API and the database have no host
port. So `https://localhost:8443/api/v1/` answers with the same JSON as A.8, through the proxy.
nginx forwards only `/api/`, so the API's own `/health` and `/docs` are not reachable from the
host on this route.

## B. Authentication

1. **Open the application**: http://localhost:5173 on Route A, or https://localhost:8443 on
   Route B. Any page you are not signed in for sends you to `/login`.
2. **Sign in.**
   - **Email address:** `demo.owner@example.com`, the seed's default owner, or whatever you passed
     as `--owner-email`.
   - **Password:** the value you set in `DEMO_OWNER_PASSWORD`. The repository contains no demo
     password and none is documented, by design. If you have lost it, reseed into a new database
     (part E).
3. **Expected result:**
   - the dashboard, titled **Overview**;
   - the sidebar groups **Operations**, **Finance**, **Intelligence** and **Administration**;
   - in the header, a **Selected hotel** list with *Demo Harbour Hotel* and *Demo Hillside Inn*,
     because the demo owner holds the `owner` role at both;
   - a sign-out button named after the account, *Demo Owner*.
4. **What it demonstrates:**
   - The browser session is three cookies, `__Host-ahip_access`, `__Secure-ahip_refresh` and
     `__Host-ahip_csrf`. The first two are `HttpOnly` and none of them can be read across sites,
     so you can see them in the browser's developer tools but page script cannot read the
     tokens.
   - Every change also needs the CSRF token in `X-CSRF-Token`.
   - API clients sign in with `POST /api/v1/auth/login` and hold a bearer token instead.

   See [architecture.md §7.1](architecture.md#71-session-handling-and-its-limitation).

## C. Core application walkthrough

Most steps only read data. The two optional steps that change it (C5 and C9) change only the
disposable demo database. Where a step names one hotel, the other behaves the same with its own
data.

### C1. The dashboard: one property at a glance

- **Navigate:** **Dashboard** (`/`).
- **Do:** change the period selector from **Last 7 days**, the default, to **Last 30 days**.
- **Expect:**
  - the **Performance** cards: Occupancy, ADR, RevPAR and Room revenue;
  - **Revenue and result**: Other revenue, Expenses, Net operating result and Guest rating;
  - an **Occupancy trend** chart and **Stay activity**;
  - **How these figures are measured**, which states each definition and the exact window.
- **Demonstrates:** every figure is computed by the server (`GET …/analytics/overview` and
  `…/analytics/daily`) over a declared window. Money is never added across currencies: amounts
  are reported per currency, and a period holding more than one is listed **By currency** instead
  of summed. Both demo hotels use EUR only.

### C2. Two properties, strictly separated

- **Navigate:** the **Selected hotel** list in the header.
- **Do:** switch to the other demo hotel, then revisit the dashboard.
- **Expect:** different figures, rooms and guests. Nothing from one hotel appears under the other.
- **Demonstrates:** tenant isolation. Every hotel-scoped query is bounded by the hotel resolved
  from your membership, and a hotel you do not belong to answers 404, exactly like one that does
  not exist ([architecture.md §2.4](architecture.md#24-tenant-isolation-in-detail)).

### C3. Bookings

- **Navigate:** **Operations → Bookings** (`/bookings`).
- **Do:**
  1. Read the paged list.
  2. Type part of a reference such as `DMO-HRB` into **Reference, room or occupant**.
  3. Filter by status.
- **Expect:**
  - each booking's reference (for example `DMO-HRB-01563`), occupant, stay, room, status,
    contracted total and channel;
  - statuses across the lifecycle: Pending, Confirmed, Checked in, Checked out, Cancelled and No
    show. On 2026-11-27 Demo Harbour Hotel had 1,584 bookings.
- **Demonstrates:** the booking model and its lifecycle. The page says plainly that its filters
  apply to the loaded page only, because the API has no server-side search to back them.

### C4. One booking, reconciled

- **Navigate:** open any **Checked out** booking from the list.
- **Do:** read the stay, the guest panel and the payments.
- **Expect:**
  - the stay: check-in, check-out, nights and occupancy;
  - the occupant's details;
  - payments, with **Contracted total**, **Charged**, **Refunded** and **Net paid**, and a payment
    status such as Paid or Partly paid.
- **Demonstrates:** server-side pricing and reconciliation (`GET …/bookings/{id}/reconciliation`).
  Payments are recorded movements, and no balance is computed in the browser.

### C5. Optional: change a booking's status

This step writes to the demo database.

- **Navigate:** a booking whose status is **Pending** (filter by status in C3).
- **Do:** choose **Mark confirmed**.
- **Expect:**
  - **Booking status updated.**;
  - the actions now offered are only the legal next steps from Confirmed: checked in, cancelled
    or no show;
  - a terminal move asks for confirmation first.
- **Demonstrates:**
  - The lifecycle is enforced by the server, not the button list: an illegal move such as
    *confirmed → checked out* is refused with `409 CONFLICT` ("A booking cannot move from
    confirmed to checked_out.").
  - The change is recorded in the hotel's audit trail as `booking.status_changed`, readable by a
    manager through `GET /api/v1/hotels/{hotel_public_id}/audit-events`. No screen shows a
    hotel's audit trail.

### C6. Guests

- **Navigate:** **Operations → Guests** (`/guests`), then open one guest.
- **Expect:** the people on file at this property, and on the detail page their contact details,
  preferred language, notes and **Marketing** consent.
- **Demonstrates:** a guest record belongs to one property. The same person at the other hotel is
  a separate record, so no guest data crosses hotels.

### C7. Rooms

- **Navigate:** **Operations → Rooms** (`/rooms`).
- **Expect:**
  - Demo Harbour Hotel's three room types, `DBL` Standard Double, `SEA` Superior Sea View and
    `STE` Harbour Suite, each with a base price, beds, size and sleeps;
  - the rooms of each type with their operational status.
- **Demonstrates:** the room catalogue. A room's operational status is kept distinct from whether
  it is free on a given night.

### C8. Availability

- **Navigate:** **Operations → Availability** (`/availability`).
- **Do:** choose a check-in a week ahead and a one-night stay, then **Search availability**.
- **Expect:** whether the request can be met, and the free rooms per room type. On 2026-11-27, a
  one-night stay a week later at Demo Harbour Hotel had 5 rooms free across 2 room types.
- **Demonstrates:** the answer comes from the database. A GiST exclusion constraint over
  half-open date ranges makes two overlapping allocations of one room impossible
  ([database README §7](../database/README.md#7-booking-overlap-strategy)).

### C9. Financials

- **Navigate:** **Finance → Financials** (`/financials`).
- **Expect:** the revenue journal and the expense journal, each with per-category, per-currency
  totals and no overall total.
- **Optional (writes):** **Create entry** posts a new line.
- **Demonstrates:** an append-only ledger. A posted line is corrected by posting another, never by
  editing or deleting it: the API has no route that edits or deletes a revenue or expense line.

### C10. Analytics, and the served demand model

- **Navigate:** **Intelligence → Analytics** (`/analytics`).
- **Do:**
  1. Pick a period.
  2. Read **Performance**, **Activity** and **Revenue and expenses**.
  3. Narrow the browser window, then press Tab until the expenses table is focused, and use the
     arrow keys.
- **Expect:**
  - **Performance:** Occupancy, ADR, RevPAR and Room revenue for the period.
  - **Activity:** **Bookings created** and **Arrivals**.
  - **Revenue by category** and **Expenses by category:** tables with the columns Category,
    Currency, Amount, Tax and Entries, and no total row.
    - A fixed cost such as `PAYROLL` carries a **Fixed cost** tag.
    - From 768px up, both tables fit inside their cards; the tag wraps under its code when space
      is short.
    - On a phone-width window a table scrolls sideways inside its card. Its box is then a
      focusable region named after the table, so the keyboard can reach and scroll it.
  - **Demand estimate**, labelled **Modelled estimate — not a recorded figure**:
    - tomorrow's date, the forecast horizon and the cutoff the model read up to;
    - the model version `demand_baseline_v1`;
    - the statement that the model is not production ready and that its accuracy against real
      hotels has not been established.
  - For both demo hotels the estimate also shows **Above this hotel's capacity**. On 2026-11-27
    the model predicted about 128 room nights for a hotel with 15 or 10 rooms.
- **Demonstrates:**
  - Period reporting with no arithmetic in the browser.
  - The one screen that asks the trained model anything (`GET …/ml/demand-forecast`), each answer
    stored as a prediction row. Viewing this screen writes one such row to the demo database,
    the model's only declared write.
  - The capacity warning is the model's known limitation, visible on screen. It was trained on two
    large hotels, and it cannot tell small hotels apart.
  - **Fixed 2026-11-27:** the expenses table used to clip its last column at 1440px. It no longer
    does, and five table checks in CI's responsive audit fail the run if it regresses.

### C11. Reviews

- **Navigate:** **Intelligence → Reviews** (`/reviews`).
- **Expect:** the rating distribution in five normalized bands, a breakdown by channel, and the
  reviews themselves (452 at Demo Harbour Hotel on 2026-11-27).
- **Demonstrates:** reviews from channels with different scales, made comparable without editing
  the guest's own rating or text.
- **Not implemented:** **review sentiment analysis**. No polarity, aspect or text model exists,
  and none is implied.

### C12. Forecasting: the statistical layer

- **Navigate:** **Intelligence → Forecasting** (`/intelligence`).
- **Do:** change the horizon ("Starts tomorrow. The API allows at most 90 days.") and the
  **Training history**.
- **Expect:**
  - an occupancy forecast with its interval, shown *beside* what is already on the books, never
    blended into it;
  - a revenue forecast;
  - a demand trend, with both window medians and the threshold, so its direction can be checked
    by hand;
  - anomalies and findings;
  - the **attention list**, the busiest upcoming days and the strongest anomalies, each with its
    source and a stated limitation.
  - In the forecast-performance part, a fresh database has nothing scored yet: "No predictions in
    this window were scored, so there is no error to report." Stored predictions are scored only
    after a 28-day settlement lag.
- **Demonstrates:** the V1 intelligence layer. It is deterministic (seasonal-naive day-of-week
  medians, MAD intervals and modified z-scores) and uses no language model. The same question
  always gets the same answer. See
  [architecture.md §5](architecture.md#the-statistical-intelligence-layer-stage-3b11) and
  [attention-list.md](attention-list.md).

### C13. Copilot

- **Navigate:** **Intelligence → Copilot** (`/copilot`).
- **Expect, by default:** **The copilot is switched off in this deployment**. The API answers
  `503 LLM_DISABLED`, and `GET /api/v1/` reports `"copilot_enabled":false`.
- **Demonstrates:** the language-model boundary is off unless an operator switches it on, and no
  model is called by CI or by the shipped image.
- **Optional, Route A only, not verified for this walkthrough:**
  - Start the API with `LLM_ENABLED=true` and `LLM_PROVIDER=ollama`, with Ollama running locally.
    `OLLAMA_BASE_URL` must be a loopback address, so this does not work from inside the Docker
    stack.
  - Questions are then answered through seven read-only tools, and every answer is labelled
    generated.
  - The seed creates **no** knowledge documents. Document questions therefore have nothing to
    cite until documents are uploaded through `POST …/documents`; the UI only reads them.
  - The copilot's answer quality with a real model is **not** established
    ([copilot-evaluation.md](copilot-evaluation.md)).

### C14. Administration and platform

- **Navigate:** **Administration → Property** (`/property`), **Administration** (`/administration`)
  and **Platform** (`/platform`).
- **Expect:**
  - **Property:** the hotel's record, its room types, rates and amenities.
  - **Administration:** your account, **Change your password**, and the member list. The demo
    owner is the only member.
  - **Platform:** the shared catalogues, **Amenities** (7 in the seed), **Revenue categories**
    and **Expense categories**, which any signed-in user can read.
    - With the optional grant (A.9), you can also write to them, and the platform audit trail
      shows the `platform_admin.granted` event.
    - Without it, the page says "The platform audit trail needs a platform administrator grant",
      and writing a catalogue is refused for the same reason.
- **Demonstrates:** the role hierarchy (viewing members needs manager, changing them owner),
  and a platform-administrator capability kept separate from every hotel role.

- Read [architecture.md](architecture.md): §2 for the layering, §2.4 for tenancy, §2.5 for

### D4. Frontend architecture

- `frontend/src/router/navigation.ts` defines the sidebar.

- One API client lives in `frontend/src/services/api/`.
- Read [frontend/README.md](../frontend/README.md) and [ui-redesign.md](ui-redesign.md), which
  also covers the responsive audit in `frontend/e2e/`.

```bash
cd frontend && npm test && npm run typecheck && cd ..
```

## E. Reset and cleanup

**What is disposable, and what is not:**
- **Disposable demo data:** the database you created in A.3, or the Compose volume of Route B,
  holding only the synthetic seed and whatever you did during the demo. That includes C5, C9, and
  the prediction rows C10 wrote.
- **Disposable test databases:** the `*_test` databases created by `scripts/testdb.py`, which the
  integration suite empties.
- **Everything else is user data:**
  - Never seed into, migrate, drop or point `TEST_DATABASE_URL` at a database you did not create
    for this purpose.
  - The seed refuses a database that holds any row, and it never deletes anything.

**Route A:**
1. Stop the API and the dev server with `Ctrl+C` in their shells.
2. To reset the demo, the seed never overwrites: **create a new database**, then migrate and seed
   it (A.3–A.5), and point `DATABASE_URL` at it.
3. Drop the old one yourself, only once you have confirmed nothing in it needs keeping:

   ```bash
   psql -U postgres -c "DROP DATABASE hotel_intelligence_demo"
   ```

4. Drop a scratch test database with `.venv/Scripts/python.exe scripts/testdb.py drop
   walkthrough_scratch_test`. It refuses anything that has not cleared its safety guard.

**Route B:**
- `docker compose down` stops the stack and **keeps** the database volume.
- `docker compose down -v` stops it and **permanently destroys** the volume, and with it the demo
  data. After that, `docker compose up -d --build` and A.14 give a fresh demo.
- The `certs/` directory and `.env` are local and git-ignored. Delete them when you are done if
  you no longer need them.

See [database README: Resetting safely](../database/README.md#resetting-safely) and
[deployment/backup-restore.md](deployment/backup-restore.md).

## Limitations to state during the demo

- **Portfolio scope; not production ready.** The closure audit lists what production would need.
  - No automated backups, certificates or alerting.
  - No zero-downtime deploys.
  - Open registration, where creating a hotel makes you its owner.
  - Twelve owner decisions still open.

  See [project-closure-audit.md](project-closure-audit.md) and
  [README: Known limitations](../README.md#known-limitations).
- **Synthetic data.** The demo hotels and everything in them are generated. Nothing seen in the
  demo is evidence about real hotels.
- **The served model is implemented, not validated.**
  - Its production accuracy, reliability and generalisation are not established.
  - It is not claimed to beat the statistical baseline.
  - It ignores capacity, as C10 shows.
  - There is no drift detection, alerting or retraining.

  See [ml-model-card.md §15](ml-model-card.md).
- **Retrieval quality on real documents, and the copilot's answer quality with a real model, are
  not established.**
  - The retrieval corpus and most of its queries are invented.
  - Paraphrased queries are not found.
- **Not implemented:** review sentiment, room-image classification, guest recommendations, vector
  search or embeddings, agents, and any copilot tool that writes business data.
- **Fixed:** the Analytics expenses-table clipping, since 2026-11-27 (C10).
